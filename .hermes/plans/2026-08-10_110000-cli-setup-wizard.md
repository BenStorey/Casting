# CLI Setup Engine + Interactive Wizard — Implementation Plan

> **For Hermes:** implement with TDD; commit; push. Build the shared *setup
> engine* first, then the interactive CLI driver on top.

**Goal:** `cast init` becomes a real onboarding flow — an owner configures the
company (name, initial cast, objective, owner token, optional starting
governance) and it produces the initial event sequence in the state store. The
engine is shared so the future first-run UI drives the *same* logic.

## Architecture (the "both, one engine" decision)

- **`src/setup.rs`** — the deterministic *setup engine*: a `SetupSpec` struct
  (name, objective, cast role-ids, owner token, optional directives) + a
  `SetupPlan` that, given a state dir, **idempotently** writes the initial events
  (ProjectCreated, AgentHired per chosen/cast role, optional directives) into
  the store. Reads the existing projection so a re-run never double-hires.
- **CLI driver** in `main.rs`: `cast init <dir> [--interactive]` and/or
  `cast init <dir> --name=… --objective=… --cast=engineer,qa --owner-token=…`.
  Interactive mode prompts for each field; flag mode is scriptable/headless.
- The **UI first-run** (later) will call the same `SetupPlan` — no second copy.

## Important design decision: setup ≠ onboarding

`plan_onboard` runs when the OWNER sends the first message. The setup engine
should NOT duplicate that — it:
1. creates the company (ProjectCreated),
2. hires the chosen cast members (AgentHired),
3. sets owner auth (token),
4. optionally writes starting governance directives.

It does **not** fire the objective/MessageSent — that stays the owner's first
real message, which triggers `plan_onboard` (which now hires *remaining* cast,
skipping already-hired). To keep them from fighting, `plan_onboard`'s cast
hires must be made **idempotent** (skip an agent already in the projection).
